## 1. `run --batch` — delivered (PR #131, merged 11/06/2026)

NDJSON proposals in, one per line: `{transformation, actor, args_named}` (actor *per row*, not a flag — an import file carries mixed provenance); the pinned per-proposal outcome envelope out, order-preserving; continue-on-rejection by default with `--fail-fast`; one parse+validate and one connection pool per batch.

**Semantics pinned explicitly: each row is its own SERIALIZABLE transition.** A batch is N independent proposals with amortised transport, never an all-or-nothing import. Atomic multi-trade admission would be one governed transition with many statements — a semantics question, to be raised separately if ever genuinely forced. Glasshouse's Imports workbench is designed to this: partial success is the normal outcome, surfaced per row.

Acceptance: the upstream embedder-latency harness.

Delivered with one deliberate contract divergence from single run: a batch exits 0 whenever every row was processed - rejections and malformed-row error receipts are results in NDJSON (the pinned envelope plus `row`, with a third `{"status": "error"}` variant), and non-zero is operational only; a 40001 serialization conflict is a re-submittable row receipt, not an abort. Surfaced as `run_batch(rows)` on the generated client (section 9), returning one `BatchReceipt` per row. First Glasshouse consumer shipped 11/06/2026: `glasshouse.imports` (the trades CSV path - quarantine locally, one batch invocation, per-row receipts mapped back to file lines in the import report).

## 2. `morpholog hash` — accepted, mechanism corrected

The hash is over the *canonical source* (`format(parse(source))`, the round-trip property as canonicaliser), not internal IR — so the hashed artefact is a human-inspectable `.morph` file, and the hash is **rules-identity, not file-identity** (formatting and comments vanish). Exactly the right semantics for `ruleset_version` in curve identities and evidence packs, and for a deployment pinning "built against model hash X".

## 3. `schema --all` manifest — accepted, merged with 2, improved

One JSON artefact: `{model_hash, program, transformations, intents, predicates}` — predicate declarations included, so the read side's field-name decoding is fed by the same manifest. One codegen input for the generated Pydantic models and typed decoders; one CI drift-check artefact.

## 4. `inspect claims --where` — deferred in favour of generated per-predicate SQL views — delivered upstream (PR #145) and adopted 26/06/2026

Upstream generates `CREATE VIEW` per predicate with declared column names, versioned with the model and stamped with its hash. This replaces what would have been raw positional-JSONB reads on Glasshouse's side (which break silently when a predicate changes shape): **the generated views are the official inspection surface for governed state** — audit, reference lookups, and the adopter BI story in one move. Glasshouse is the forcing example for the generator. Projections remain the primary read model; the views are the inspection model.

**Adopted 26/06/2026** (in the same PR that re-pinned `MORPHOLOG_REF` `f414660` → `1c9fc93`): `morpholog generate views <MODEL_FILE>` is committed byte-exact at `glasshouse/commit/morpholog_views.sql` (9 base views + a `_morpholog_catalog` that stamps the same `MODEL_HASH` the Python client names), applied by `commit.apply_views()` (a transactional script run on one autocommit psycopg3 connection — the programmatic `psql -v ON_ERROR_STOP=1`), exposed as `glasshouse apply-views` and reset by `provision()`. Drift is closed two ways in the integration leg, exactly like the generated client: regenerate-and-diff against the committed `.sql`, and a fifth `glasshouse verify` leg (`views`) asserting the live `morpholog_views` catalogue still names `MODEL_HASH`. The binary owns the positional JSONB mapping, so law 4's "never read governed state via raw positional JSONB" is honoured by construction. The derived-view half (`refresh derived`, PR #146/#147) stays unadopted: the needle has no derived predicates (MTM is computed in the compute zone, not by the kernel).

## 5. Higher-order authority (WP2) — enthusiastically flagged, parked

Glasshouse's ledger-resident capability model ("who could approve corrections last March" as an as-of query) is the worked example that must arrive *before* the WP2 design: patterns over transformation names are claims-about-rules — constitutionally novel territory, example-first. The per-capability grant boilerplate Glasshouse accumulates is precisely the pressure pattern-based authority needs to see.

## Asks 6-8: drafted and delivered 07/06/2026 (upstream PR #125, merged)

Surfaced by building `glasshouse.commit` against the real binary; each named the business shape that forced it, per the substrate's own doctrine. All three were delivered the same day in PR #125, verified against the rebuilt binary, and adopted in `glasshouse.commit`.

### 6. Schema provisioning from the binary (`morpholog init`) — delivered

The ask: the binary could not initialise its own database; a fresh database needed `crates/morpholog-core/sql/schema.sql` from a source checkout at the matching commit, and the Glasshouse Docker image (binary only) had no drift-checked provisioning path. Delivered better than asked: the canonical schema travels inside the binary (`include_str!`), day-zero only, refuse-or-skip on an existing schema (`--skip-if-exists` for re-runnable entrypoints), never drops, never migrates. Adapter surface at delivery: `MorphologAdapter.init()` (today `Morpholog.init()` on the generated client, section 9).

### 7. Named claim args on the read surface (`inspect claims --named`) — delivered

The ask: `--args-named` made the write side bare and named while the read side stayed positional and tagged, so every embedder re-implemented zip-by-declared-order plus an arity guard. Delivered with a deliberate authority flip: the bare read keeps the claims table as authority (unknown predicate = empty); under `--named <file.morph>` the programme is the authority, so a requested-but-undeclared predicate fails before any database read and programme/database skew is a hard error naming both sides. Values are wire-true (decimals and dates stay strings); typing belongs to the generated per-predicate models fed by the `schema --all` manifest. Adapter surface at delivery: `read_claims`, a thin pass-through once the hand-rolled decode was deleted (upstream deleted the worked embedder's identical helper in the same PR; today `claims_named` on the generated client, section 9). The positional shape still recurs in run envelopes and the audit log; whether the projector wants the same treatment is a separate, separately-forced question.

### 8. Same-snapshot explanation on rejection (`run --explain-on-reject`) — delivered

The ask: the API promises every rejection a structured reason and an answer to "what would make this admissible?", and run-then-explain is two snapshots that can disagree under concurrent commits. Delivered with exactly the right semantics: the rejecting proposal hands back the scoped pre-state its gates evaluated, and the pure explanation engine runs against it in memory; rejection envelopes gain an `explanation` field in the `explain --json` shape; committed envelopes and exit codes unchanged; kernel errors and serialization failures excluded (no admissibility story). Adapter surface: `run(..., explain_on_reject=True)`, surfaced as `Rejected.explanation`.

## 9. The generated Python client lives in the binary (`morpholog generate python-client`) — delivered (PR #133, merged 11/06/2026; filed 07/06/2026 as [morpholog#126](https://github.com/jordan-dimov/morpholog/issues/126))

Delivered as specified, including the stdlib-only amendment, plus two additions: `schema --result` (the machine-readable outcome-envelope contract, the consumer that unreserved it) and `check --json` from PR #132 (every parse/validation/lint finding as data with byte offsets and line/column, surfaced as `check(strict=)` returning a `CheckReport`). Adopted same day: the five-file `morpholog_client/` package is generated into `glasshouse.commit`, committed byte-exact, and drift-checked by regenerate-and-diff in the env-gated integration leg plus a `MODEL_HASH ==` `morpholog hash` assertion; `envelope.py`, `adapter.py`, `bases.py`, the codegen script and the golden captures are deleted, exactly as the ask predicted. Envelope parsing is key-set strict by design (unknown field = "regenerate" error, the drift tripwire). Pydantic now appears only at the HTTP boundary, built from the generated types. The original ask follows.

### The forcing example, quantified

Glasshouse, the first external embedder, has now built the complete Python integration twice (once hand-rolled, once after adopting asks 6-8) and the remaining surface measures as follows: 612 lines of hand-written interface Python (codecs, envelope models, subprocess adapter, model generator) plus 665 lines of tests and golden captures defending them, around a 174-line `.morph` that is the only genuinely Glasshouse artefact at the boundary. Roughly 7x as much Python protects the boundary as there is content crossing it, and **none of those 612 lines is embedder-specific**: every one is mechanically derivable from artefacts Morpholog already owns.

- The tagged-value codecs (both directions) derive from the pinned codec contract; they vary only with the binary version.
- The envelope models (`Committed | Rejected`, the Explanation shape, named claims) derive from the pinned envelope contract; same.
- The adapter (command construction, the empty-stdout discrimination rule, `init`/`run`/`explain`/`inspect`/`hash`) derives from the pinned CLI contract; same.
- The typed request and read models derive from the `schema --all` manifest; they vary only with the `.morph`.

The two worked Python embedders (upstream's own and Glasshouse) have therefore converged on writing the same client - the bar that forced `inspect claims --named`.

### The ask

`morpholog generate python-client --out <dir>` (taking the `.morph`): the binary emits a complete, self-contained, typed Python client package - codecs, envelope models, the subprocess adapter, request models per transformation, read models per predicate - stamped with the binary version and the model hash. The same move as `init`: the schema travelled into the binary so a deployment provisions exactly what its build expects; here the *client* travels with the binary so an embedder talks exactly the contract its binary speaks. No PyPI release treadmill, no version skew by construction, no FFI, the subprocess contract unchanged underneath.

The embedder's whole integration becomes: generate, commit the package, drift-check in CI by regenerating (pure, given the committed manifest) plus one `hash` comparison against the live binary. Glasshouse's existing layer is, almost verbatim, a prototype of the output (and is offered as the seed); its golden envelope captures become the generator's own contract tests.

### What this forces alongside

- **`schema --result`** (currently reserved upstream, awaiting "a real consumer that needs to discriminate dynamically"): the client generator is that consumer - it wants to generate the outcome models from a machine-readable contract rather than have them hand-pinned from documentation.
- Nothing else: batch, views, the audit-log shape are all orthogonal and the generated adapter adopts them as they land.

### Non-goals, stated to keep the ask small

In-process bindings (PyO3/FFI) are explicitly not asked for: the ~9ms subprocess tax is not the pain, the hand-maintained glue is. Other languages (TypeScript) follow whenever their worked example arrives; the command name leaves room.

### Targeting (amended on the issue, 07/06/2026)

The generated client is **stdlib-only** (frozen dataclasses, Decimal/datetime from stdlib, validation emitted as plain code), so the dependency question vanishes rather than being answered, and the worked embedder keeps its stdlib-only property. The Python version is a **declared, enforced, CI-tested floor**: stated in the generated header, checked at import time, exercised in upstream CI at the floor, emitted as a conservative subset so the floor moves only deliberately. Consequence for Glasshouse at adoption: Pydantic moves to the HTTP boundary, where API request models are built *from* the generated types (org from auth context, actor from session, never from a request body) - DESIGN.md section 7's "generated Pydantic request models" sentence gets re-pointed at that boundary then.

Minor nit to bundle: PR #124's text promises manifest entries in declaration order; the binary emits the transformation and intent maps alphabetically. Byte-stable either way; the docs and behaviour should agree.

## 10. Language tiers landed upstream 09/06/2026 — disciplines adopted, `define` parked

Not Glasshouse asks; upstream language growth (PRs #129 and #130) adopted under the standing rule of taking each surface as it lands. Verified against the rebuilt binary before adoption.

### Claim disciplines (PR #130) — adopted in the needle model same day

Claim-shape law declared on predicates instead of authored invariants: `unique by (fields)` (the keys determine the whole claim), `append only` (retraction is a static authoring error), `current pointer by (fields)` paired with `superseded via <Lineage>` (the singleton pointer plus no-fork on the two-argument successor/prior lineage predicate). Six of the needle's twelve invariants were exactly these shapes and are now discipline clauses: capture/terms/registration/valuation uniqueness, the official-pointer singleton, and no-fork lineage. `inspect guarantees` confirms the generated invariants are semantically identical to the deleted ones, each traced to its clause (`from: predicate OfficialCurve, current pointer by (org, market, as_of)`); the six referential and value invariants stay authored, as no discipline claims them. The doctrinal gain: law 2 (supersede, never overwrite) is now machine-enforced on the record predicates, not a convention the transformations happen to respect. The capability predicates carry no discipline on purpose: revocation, when it arrives, is a governed retraction that `append only` would forbid.

Wire impact, verified: the `disciplines` array on manifest predicate objects is serialised only when present (an undisciplined model's manifest is byte-identical), the codegen passes it through untouched, generated model shapes are unchanged, and only the model hash re-pins. Additive for the in-flight #126 client generator. The new lint tier (`check` prints `hint:` lines to stderr, `--strict` promotes them to errors; stdout stays empty on success) joins the env-gated integration leg as a strict check, since CI's pure leg never runs the binary.

### `define` (PR #129) — deliberately not adopted yet

Named, parameterised conditions callable from gates and invariants, proposition-valued only. The needle repeats no condition complex enough to name, so adoption now would be decoration. The forcing case is already visible: upstream's `terms_in_force_on` is precisely the versioned-terms selection the amendment milestone needs, at which point `TradeTerms` also loosens from `unique by (trade)` to `(trade, effective_from)`.

## 11. `--as-of` on the generated read surface — delivered (PR #138, merged 11/06/2026; filed same day as [morpholog#135](https://github.com/jordan-dimov/morpholog/issues/135))

The binary's `inspect claims --as-of` (a transition id or an RFC 3339 timestamp, replayed correctly) has been load-bearing for Glasshouse since the first integration pass: the needle's as-of query ("as-of the registration transition, v1 was the official curve") is a headline capability, exercised in the integration lifecycle. The generated client's `claims`/`claims_named` did not expose the parameter; `GlasshouseClient` bridged the gap by hand-building the inspect command. Delivered as asked (`as_of: str | None = None` on both reads) and adopted same day: the hand-built command is deleted and `GlasshouseClient.read` is now a thin typed composition over the blessed surface (the subclass itself stays - binary discovery under `GLASSHOUSE_MORPHOLOG_BIN` and the typed-read convenience are Glasshouse's own, not gaps). The same upstream pass (#137) gave the client `coverage()` (`inspect coverage`: per-invariant did-its-condition-ever-match, per-transformation usage, over replayed history); the integration lifecycle now asserts every transformation in the needle has done work by its end.

## 12. The audit-log read contract — delivered (PR #142, merged 11/06/2026; filed as [morpholog#136](https://github.com/jordan-dimov/morpholog/issues/136))

Upstream deliberately left the audit surface unpinned, "pending the worked example that forces the shape". The Glasshouse projector (`glasshouse.projections`, 11/06/2026) is that example: it tails `morpholog.audit` ordered `(committed_at, transition_id)` (the same causal order `morpholog verify` replays), reads `transition_id`/`asserted_claims`/`retracted_claims`/`committed_at`, and decodes the `{predicate, args}` tagged-claim shape with the generated client's own codecs. The ask, filed as morpholog#136: pin the table's read contract (columns, claim shape, ordering guarantee, stable-vs-reserved), or bless an `inspect audit --after --named` NDJSON surface that the generated client could then carry - which would also give projectors the named decode for free. No new semantics: the data and ordering already exist. Until one of the two lands, the projector documents that it reads an unpinned surface.

## 13. An operation timeout on the generated client — surfaced by the readiness probe, filed 11/06/2026 as [morpholog#140](https://github.com/jordan-dimov/morpholog/issues/140)

The generated `_invoke` runs the binary unbounded, which is right for batch imports and wrong for a readiness endpoint: a binary that answers `--version` and then hangs on `inspect claims` would turn `/readyz` into a stuck request instead of a fast 503. Bridged by `GlasshouseClient` (the same pattern as the as-of bridge that #138 deleted): an optional `timeout_seconds`, unset by default, enforced in an overridden `_invoke` that mirrors the generated semantics and converts `TimeoutExpired` into the operational `MorphologError`; the API boundary sets it from `GLASSHOUSE_MORPHOLOG_TIMEOUT_SECONDS` (default 10s). The ask, filed as morpholog#140: a constructor `timeout` on the generated client, enforced in `_invoke`, after which the override deletes.

## 14. The generated client catches up again: `verify` and batch explanations — filed 11/06/2026 as [morpholog#141](https://github.com/jordan-dimov/morpholog/issues/141)

Surfaced by the explainability pass. `glasshouse verify`'s ledger leg needs `morpholog verify` (pinned, but absent from the generated client - bridged by `GlasshouseClient.verify_ledger` over the inherited `_invoke`, whose empty-stdout rule already fits the verdict-on-stdout-at-exit-1 shape). The import reports' per-row whys need `--explain-on-reject` composed with `--batch` (the CLI supports it, the envelope already parses it, the generated `run_batch` exposes neither it nor a timeout - bridged by an override duplicating the generated body plus one flag, the drift-prone copy the generated client exists to delete; the timeout half is the #140 family). Both bridges delete on delivery, as the as-of bridge (#135 -> #138) did. One more for the family: the generated audit tail (`_audit_lines`, section 12) deliberately bypasses `_invoke` (an empty tail is lawful empty stdout, so discrimination is on the exit code alone), which means the #140 timeout bridge does not bound it - #140's eventual delivery should cover the tail's subprocess too.

## 15. The `propose` rename (#143) and the rejection log (#139) — 12/06/2026

`run` is now `propose` (no deprecation alias: two names for one act is drift), `parse` folds into `check --ir`. What did NOT change, by upstream's deliberate choice: every envelope byte, every exit code, the batch receipt contract, and the wire names (`run_outcome` and `parse_run_outcome` keep their names - envelope identity is contract identity). Adopted by regeneration: Glasshouse's typed commit path goes through `submit()`, which is untouched, so the only renames were our own `propose_batch` bridge (section 14) and its tests. No Glasshouse script shells `morpholog run` directly.

The rejection log (#139): `morpholog.rejections` records one row per refused proposal AFTER rollback - transformation, arguments, actor, `kind` (invariant/require/bind), `rule`, the envelope reason, `rejected_at` - structured at the source, no display-text parsing. Honesty bounds to mirror in any future consumer: OPERATIONAL evidence, at-most-once, a floor not a census; the audit table stays the only legitimacy-grade record. Deliberately unadopted until the number-defence screen consumes it. `coverage()` now reports `constrained` (a rule that refused at least one real proposal) and `rejections_replayed` is required in its envelope - absorbed by regeneration; Glasshouse pins the coverage shape nowhere else.

## 16. Re-pin `f414660` → `1c9fc93` and the `verify` envelope restructuring — 26/06/2026

The first re-pin since the generated client landed, forced by adopting the views generator (section 4). Two facts established by regenerating against the new binary: the generated Python client is **byte-identical** (the drift gate confirms the +71-commit span made no wire change to the client surface — `submit`/`explain`/`claims`/`audit`/`coverage` all unchanged), and `check --strict` on the needle model stays clean (so #144's dead-antecedent lint, additive to the strict-check leg, finds nothing and rides along for free). No bridge deletions are reclaimable: the generated client still carries no `verify`, no constructor timeout, and no batch-explain, so the section 13/14 bridges all stand.

The one forced change: the tamper-evident audit work (upstream #159) **restructured the `morpholog verify` envelope**, `{"status", "only_in_*"}` → `{"replay": {status, claims, transitions}, "tree": {status, checkpoints, tree_size}}`. Because `verify` is bridged, not generated, the regenerate-and-diff gate could not catch this — it surfaced only when the new binary's verdict stopped parsing (a concrete argument for section 14: a generated, typed `verify` would have made the break loud at re-pin). `verify_ledger` + `verify.py`'s ledger leg now read `replay.status`. The `tree` verdict is the tamper-evidence seam: deliberately not surfaced yet (with zero checkpoints the tree is trivially intact), it seeds the next substrate PR — `checkpoint` creation + a `glasshouse verify` tree leg + the offline evidence pack (#159/#161), the regulator-grade legitimacy slice.

**Drift now has an early-warning sensor** (added in the same PR): `.github/workflows/substrate-canary.yml` runs the full live suite against morpholog HEAD on a weekly schedule (and on demand), non-blocking and off the PR gate. The CI integration job stays on the pin for reproducibility; the canary surfaces a reshaped envelope, a renamed verb, a regenerated client or view surface, or a model-hash change as a red run *before* the next re-pin, instead of at it. A red canary is the signal to adopt the new surface deliberately (or report the friction upstream), not an emergency.

## 17. The whole consumed surface is generated and typed — re-pin `1c9fc93` → `8e090e8`, all bridges deleted — 28/06/2026

Sections 13 and 14 are **delivered**, and then some. Upstream made every surface Glasshouse consumes a generated, typed method under the drift gate ("a consumed surface is a pinned envelope (bridges are silent landmines)", their adoption of our verify-drift lesson): the operation timeout (#165), batch `explain_on_reject` (#172), the typed `verify` (#166, `VerifyReport` = `replay` ⊎ `tree`), the audit tail, the tamper-evidence family (`checkpoint`, `evidence_export`/`evidence_verify`, #169/#170/#173), and **credential redaction in every raised message** (#182, the `--database-url` value masked - the last forced bridge, the thin `_invoke` redaction seam). So `client.py` lost all four bridges (`_invoke`, `propose_batch`, `verify_ledger`, `_audit_lines`); what remains is genuinely ours and duplicates nothing: binary discovery, the typed as-of `read`, and `export_evidence_pack` (the binary writes the pack to stdout, we write those exact bytes to a file - the one thing the typed `evidence_export` does not do). The model hash is unchanged, so the committed views surface stayed byte-identical.

`glasshouse verify` is now **six legs**: model, ledger (`VerifyReport.replay`, typed - the divergence lists are richer than the old counts), **tree** (`VerifyReport.tree`, the Merkle history-tree verdict, meaningful once `glasshouse checkpoint` has anchored a row), projections, payloads, views. And the legitimacy slice landed bridge-free: `glasshouse checkpoint` anchors the tree, `glasshouse evidence-export` writes a portable pack, `glasshouse evidence-verify` recomputes the Merkle root offline (no database). **Signed tree heads stay the next PR**: they need an `AuditSigningKey(key_id, purpose, public_key)` predicate + a governance transformation in `glasshouse.morph` (a model change → `MODEL_HASH` bump → regenerate client *and* views), key generation, and private-key secret management - a distinct cryptographic-key-governance concern.

Two asks filed from this pass, both forced-by-example: **#182 credential redaction** (delivered same day - the generated client now masks credentials in every operational-error path, so our `_invoke` wrapper deleted), and **#184 a view-surface hash** for `generate views` (the read-side analogue of `model_hash`: hash the view definition read back via `pg_get_viewdef`, so an in-place `CREATE OR REPLACE` under the same name - which the catalogue + model-hash cannot see, the gap in `verify.py::_views_leg` - is caught). `VerifyReport.replay`'s divergent verdict carries the full `only_in_claims_table` / `only_in_replay` claim lists (our counts are just their `len()`), confirmed no regression.

## 18. The sealed view surface (#184 delivered as upstream #190) and selective evidence packs (#191) — re-pin `8e090e8` → `6556a6c`, 20/07/2026

The substrate canary did its job for the first time: two consecutive red Monday runs (13/07 and 20/07, same two drift tests) named the client and views drift a week before this re-pin, so the adoption arrived deliberate, not surprised. Upstream #190 delivered our #184 ask and then some: the generated view script now **seals itself** at apply time (each view's definition hash *as PostgreSQL stores it* - `pg_get_viewdef` read back, catalogue included - recorded into `_morpholog_view_defs` in the same transaction that creates the views), and `verify --views-schema <schema>` cross-checks intended inventory, seal and live views, so a view redefined in place under the same name (invisible to catalogue + model hash, the documented gap in `verify.py::_views_leg`) reports `tampered` naming it. The verdict rides the pinned envelope contract: `VerifyReport` gains an optional `views` leg (`ViewsIntact | ViewsTampered | ViewsNotSealed`).

Adopted: views script and client regenerated (envelopes + adapter only; model shapes and `MODEL_HASH` unchanged, the `.morph` is untouched), and `glasshouse verify`'s views leg now composes three checks - the local catalogue hash vs `MODEL_HASH`, the local inventory, and the binary's seal verdict from the shared `verify` call. Two deliberate strictness choices, both stricter than upstream's defaults: `not_sealed` **fails** the leg (upstream passes it as predating sealing; Glasshouse's committed script seals at apply time, so an unsealed live surface is not the committed surface and one `apply-views` re-seals it), and a missing seal verdict (the shared call failed operationally) means the leg **cannot claim ok** - the local checks still report their evidence, but "ok" now means unredefined, which only the seal attests.

One bridge is back in `client.py` (the #135/#140/#141 family): the generated `verify()` does not expose `--views-schema`, so an override mirrors the generated body plus the one flag. Filed as [morpholog#192](https://github.com/jordan-dimov/morpholog/issues/192); delivered and deleted in section 19. One embedder gotcha pinned in `apply_views`: the seal SQL contains `format('%I.%I', ...)`, and psycopg only leaves literal `%` untouched when no parameter set reaches the DBAPI cursor - `exec_driver_sql` passes one, so the script now goes to the raw cursor with no parameters (upstream's documented path is psql, which never interprets `%`; no upstream ask, the fix is embedder-side by construction).

## 20. The release channel and the writer-set assertion — pin `35322d9` → **v0.0.3**, 26/07/2026

Two firsts in one pass: the pin is a **released version** rather than a commit SHA, and a live deployment produced the first upstream ask that was already answered before we asked it.

**The forcing failure.** The Render demo's nightly `seed --reset` and its background projector both died with the same refusal:

> `1 session(s) in pg_stat_activity are hidden from this role, so a lossless audit resume horizon cannot be computed; connect as the role the writers use, or grant pg_read_all_stats`

Correct, and structural on managed PostgreSQL: the platform keeps its own sessions, and neither remedy is available to an application role on Render (single default user, no `pg_read_all_stats` to grant). Every audit-tailing surface was down - the projector thread, `seed`, `verify`'s projection leg - while the service itself stayed up and healthy, which is exactly the shape of failure the horizon's refusal is designed to produce (a wrong answer would have been a silently skipped transition).

**Adopted: `--writer-role` (upstream #210).** The operator asserts the session roles that write `morpholog.audit`; the horizon is `min(xact_start)` over those roles' sessions alone. Verified rather than trusted, in the same statement that computes the horizon: the catalogue census enumerates every non-superuser role that can hold a session and write audit (directly, by inherited membership, or via a usable `SET ROLE`), and refuses an incomplete assertion, an unknown role name, or an empty one. Glasshouse carries it as `GLASSHOUSE_AUDIT_WRITER_ROLES` on the client, not per call site: it is a deployment property of the connection, like the database URL and the timeout, and binding it there makes it impossible for a new audit-tailing call site to forget - a per-call argument would pass every self-hosted test and fail only in production. `render.yaml` takes the value from `fromDatabase.property: user`, never a copied literal. Empty (every self-hosted deployment) leaves the blessed all-sessions horizon byte-identical, which the pure tests pin.

**The release channel (#211/#213) replaces the from-source pin.** The pin - version and checksum - now lives in exactly one file, `scripts/install-morpholog.sh`, which the Docker image, CI's integration leg and a developer machine all run. Before, it was duplicated as `MORPHOLOG_REF` in `ci.yml` and the Dockerfile, and a re-pin once updated only the first (section 19). The artefact is a static musl x86_64 binary (one target then; three since v0.0.9, section 23), so no Rust toolchain, no MSRV to track and no cargo cache participate in a build or a deploy; the immutability guarantee is the **checksum**, not the tag. The canary switches to the rolling `main-latest` prerelease upstream recreates on every merge, verified against its published checksum - a weaker guarantee, and the right one for a job that gates nothing.

**Regeneration verdict**: `adapter.py`, `envelopes.py` and the version line only. `MODEL_HASH` is unchanged and `morpholog_views.sql` is byte-identical (the `.morph` is untouched), and the strict check stays clean under the new lints (#212's governing-selection lint, which the needle's rules do not trip).

**One ask filed from this pass — delivered in v0.0.9, adopted in section 23**, [morpholog#249](https://github.com/jordan-dimov/morpholog/issues/249): at the time, the release channel published linux x86_64 only, so the install script refuses every other platform by name and points at the source build. Honest, but it means the channel's own day-0 promise (fresh machine to a running embedder, no Rust toolchain) holds on one platform, and not on the Apple Silicon laptops a large share of embedder-curious readers own. The ask is the same packaged artefact for linux arm64 and macOS from the same tag pipeline, one checksum per asset, the existing x86_64 asset byte-stable (Glasshouse pins its checksum), and the rolling channel covering the same set for the canary. Our side is `uname`-based selection in the install script the day the assets exist. (They exist since v0.0.9, and the selection landed with the v0.0.10 pin: three targets, one checksum each.)

**Arrivals in the span, deliberately unadopted**: `inspect derived` / `refresh derived` (#207) closes two thirds of our [morpholog#204](https://github.com/jordan-dimov/morpholog/issues/204) and arrives as generated `derived()` / `derived_named()` / `refresh_derived()` methods - adopting them is a model change (derived predicate declarations, so a `MODEL_HASH` bump and a client and views regeneration) and belongs to the screens that forced the ask, glasshouse#39, not to a deployment fix. `inspect rejections` (the remaining third) and the bounded audit tail are still open upstream. The language tier lands unused: body-level `let` (#227), `round(x, quantum)` (#230). The generated-client polish pack (#240, which fixes a cosmetic indentation wart visible in v0.0.3's output) postdates the release and arrives at the next re-pin; it is invisible to us either way, since the generated package is excluded from our formatter by construction.

**Least-privilege position, from the live deployment** (section 19 left this pending): the Blueprint deliberately runs every service on the one Render-managed default credential (`glasshouse_db_user`, database owner, not a superuser), which is what makes the writer assertion sound here - one role does all the writing, and it is the role every service connects as. Render does support additional Postgres credentials, so a per-service privilege layout is a **deliberate not-yet, not an impossibility**: Glasshouse has not provisioned or granted one, and `provision --least-privilege` additionally needs `CREATEROLE` on the connecting role, which is unverified there. The deployment claim stays withdrawn on that basis, not on a claim of structural impossibility.

**Operational consequence for credential rotation**: Render's rotation keeps the existing credential live until it is removed, so during the overlap two login roles can write audit. An assertion naming only `fromDatabase.property: user` is then *correctly refused as incomplete* by the catalogue census (that is the census working, not a bug). The rotation procedure is therefore: name **both** roles in `GLASSHOUSE_AUDIT_WRITER_ROLES` for the overlap, then drop the retired one from the list when the old credential is removed. Better a refusal than a horizon computed over half the writers.

## 21. What the first live deployment taught about the writer assertion — 26/07/2026

Section 20's adoption was correct and incomplete: the assertion works, and nothing in Glasshouse would have told us if it had not been applied.

**The hidden-session condition is intermittent.** Within a single minute the live service logged "1 session(s) ... hidden" and "2 session(s) ... hidden"; between those, the same tail read succeeded unasserted. So a deployment can be misconfigured and look perfectly healthy for hours, then refuse every ledger read at 02:30 - which is exactly what the demo did before the assertion, and what it would have gone on doing if the variable had not reached the process. Anything that depends on this configuration must be provable on demand, never inferred from a green probe.

**Two consequences adopted here.** `provision` (the pre-deploy command) now reads one audit tail, so a deployment that cannot read its ledger fails the deploy carrying the substrate's own remedy, instead of coming up healthy and serving stale reads. And the projector's readiness verdict now reads its own progress - last successful poll, consecutive failures - rather than thread liveness, which the bounded retry loop had quietly made meaningless: a projector that refused twenty-one consecutive tails reported itself healthy for a quarter of an hour.

**Worth noting for any embedder**: the substrate behaved correctly throughout. It refused rather than compute an unsound horizon, its message named both remedies, and the intermittency is a property of the managed host's sessions, not of the tail. Every failure in this episode was on the embedder's side of the line - the assertion not reaching the process, and a health check that measured the wrong thing.

## 22. The audit command group, and the end of positional decoding — pin **v0.0.3** → **v0.0.8**, 03/08/2026

The first re-pin forced by the canary rather than chosen: red on 27/07 and again on 03/08, naming the break precisely (`error: unrecognized subcommand 'verify'`). Upstream gathered `verify`, `checkpoint`, `evidence export` and `evidence verify` under one `morpholog audit <cmd>` group, on the reasoning that the commands establishing the audit log's integrity belong together. The canary did exactly the job section 18 built it for: it named the drift a week before anyone needed the surface to work.

**The rename's teeth were not the CLI, they were the method names.** The generated methods moved with the group (`verify` → `audit_verify`, `checkpoint` → `audit_checkpoint`, `evidence_verify` → `audit_verify_pack`), and `GlasshouseClient.checkpoint` is an **override** carrying this deployment's writer-role assertion (section 20). The rename turned it into a method that overrides nothing: a dead function, the `--writer-role` flag silently unsent, mypy content, and every self-hosted test still green - the managed-PostgreSQL horizon failure of section 20 reintroduced by a rename. The lesson generalises past this pin: binding deployment configuration to an override makes it impossible for a *new call site* to forget, but it also makes the binding invisible to a *renamed base*. The remedy adopted is a pure test pinning the leading argv of both checkpoint paths and the hand-built pack export, so the next regrouping fails locally instead of in production.

**`Any` was hiding a positional decode.** Upstream tightened the generated client's bare `list` and `dict` annotations into `list[object]` and `dict[str, object]`. That single honesty improvement made mypy report what `Any` had been absorbing: the projector was constructing generated read models **positionally** from audit-row arguments. Nothing on the positional audit path guards arity or field order, so a reordered predicate declaration would have filed a counterparty under `market` and corrupted the read side silently. The projector now reads `inspect audit --named` and decodes through `from_named`, which resolves fields under the programme's own authority and makes skew a hard error on the binary side. Law 4's "never read governed state via raw positional JSONB" applies to the log exactly as it does to the claims table; it simply had no enforcement there until the substrate stopped saying `Any`.

**Adopted: `migrate` (#273) in `provision`.** `init` provisions but never alters, so a governed schema laid down by an older binary stays behind it forever - and since v0.0.8 the binary detects that and refuses rather than working against a schema it does not expect. That refusal belongs to the watched deploy, not to the first workload that touches the ledger, so `provision` now runs `migrate` between the init and the views. A fresh database is already current and a current one is left alone, so the command stays idempotent. This closes the persistent-schema boundary section 19 pinned and left open: the migration path now exists in the released artefact, with no SQL to vendor.

**Regeneration verdict**: `adapter.py`, `envelopes.py`, `models.py`, the version line, and one new file (`session.py`). `MODEL_HASH` is unchanged and `morpholog_views.sql` is byte-identical (the `.morph` is untouched), so no seal churn and no views re-apply; the strict check stays clean.

**morpholog#204 is closed.** All three surfaces asked for there are now pinned generated methods: `derived()` / `derived_named()` / `refresh_derived()` (#207, section 20) and now `rejections()`. Nothing in glasshouse#39 waits on upstream any more.

**Arrivals in the span, deliberately unadopted, each with an issue rather than a silent omission**: `rejections()` plus the new `rule` and `witness` fields on every refusal (a refusal now names the rule that refused it by stable identifier, and carries the variable bindings it was reading) - filed as glasshouse#52, which owns the commit-zone and import-report layer beneath glasshouse#39's refusals panel; `Session` (#284, the resident stdio process - one warm connection and one parse for many operations) - filed as glasshouse#53, explicitly including the possibility that the answer is no, because a resident process is a failure mode a subprocess-per-call design cannot have. The language tier lands unused as usual: `if(when, then, otherwise)` (#285), `period_index` (#286), civil-date arithmetic (#283).

**One observation recorded, not filed** (no forcing case yet, and the substrate's own doctrine is that asks are forced by examples): `NamedClaim.from_json` builds its arguments with `dict(data["args"])`, which also accepts a list of pairs rather than refusing a non-object by name the way the surrounding `_strict` checks do. The projector now depends on this decode for every transition, so it is worth raising the next time we have a concrete reason to; until then it is a robustness nit on a surface the binary always emits correctly.

- **Session mode** (glasshouse#53): measured at last, on a local PG18: one-shot `propose` median 19.5 ms against 2.0 ms through `open_session`, reads 18.3 ms against 1.0 ms. That is about 17 ms of process tax per call. No Glasshouse path makes enough calls for that to matter: imports are one batch, screens make one or two reads, and the projector tails every few seconds. `Session` has no audit tail, so the projector could not use it anyway. The decision stays "not yet"; the number is now on record.
- **Witnessed checkpoints and pinned signing keys**: witnesses need an RFC 3161 authority and a trust-anchor file, and `--require-signing-key` needs signed heads, which are glasshouse#42's model change. They belong to that evidence slice.
- **Self-describing audit rows** (`parameters`, stamped from migration 014 on): additive, decoded by the generated envelope, unused. They matter the first time the model changes shape (derived claims, glasshouse#39), when history must stay readable under the old signature.
- **`check --against`**: Glasshouse runs one programme, so there is nothing to compare against.

**Friction recorded from this pass (not filed; ask first):** the compiled fragment lacks unit-carrying decimals and instant ordering (above); `generate python-client --check` is blind to stray files, and `generate views` has no `--check`; the stale-schema diagnosis covers `propose` but not `audit verify` or the audit tail, which fail on the same unmigrated schema with a raw `column "arguments_hash" does not exist`; an older binary's `propose` against a newer schema gets a raw SQL error, where its `migrate` already refuses by name ("this database records migrations this binary does not know"); the one-shot `propose` and `transact` raise the decoder's own `ValueError` on an undecodable reply after the child may have committed, where `Session` raises `MorphologOutcomeUnknown` (Copilot's finding on this PR; our marking flow keeps the payload in that case, pinned by a test); `transact` is untyped.

**`transact` adopted: a correction and its re-marks are one decision.** `compute.marking.correct_and_remark` builds one act for `correct_curve` (the curve actor) and one `admit_valuation` per trade captured on the market (the valuation actor), marks each against the corrected curve in hand, and proposes them through `transact`. `admit_valuation`'s gate reads the official pointer the first act staged, so the ledger still decides whether each mark is lawful. A refusal at any act writes nothing and gives the version id back; the refusal names the act (`AtomicRejected.act`). The payload discipline is unchanged: stored before the decision, discarded on a refusal or a known non-commit, kept on an unknown outcome. The seed's Tuesday correction uses it, so the demo's twelve valuations and the audit log keep their content, with the six re-marks now sharing the correction's `committed_at`. `correct_curve_version` stays for a correction without re-marks (the imports workbench registers only). Live tests pin both branches: a committed decision marks a buy and a sell against the correction, and a decision refused at act 2 (no valuation authority) leaves the old version official, no marks, no payload, and the version id reusable.

## 25. Keyed loads, compiled checks over units and instants, the coded non-commit — pin **v0.0.11** → **v0.0.12**, 25/09/2026

Eight merges, and two of them are what this ledger forced: morpholog#392 (compiled checks over unit quantities and timestamp order) is closed, and morpholog#396 (disjoint cases conflicting under SERIALIZABLE) has its first part, a proposal loading only the rows its body can observe, through an index. **Step 1, the binary.** Installed beside v0.0.11 from the release channel; the installer's three checksums re-pinned. `morpholog --version` prints `morpholog-cli 0.0.12`.

**Step 2, migrations 016 and 017.** On a v0.0.11 ledger `migrate --check` listed `timestamp_nanos` (016) and `value_key_v1` (017); `migrate` applied both in 0.08 s and `migrate --check` then exited 0. Neither rewrites `claims`: 016 is a function that orders stored instants, 017 the equality key every stored value now compares by, realised as an expression (`morpholog.value_key_v1(arguments -> n)`) that the managed indexes are built over, not as a stored column. The report line grows an `indexes (...)` clause. The command has no generated method and prints a plan rather than JSON, so `GlasshouseClient.provision_indexes` is a hand-built argv with a parser held to the binary's own action vocabulary (`KEEP`, `CREATE`, `REPAIR INVALID`, `SATISFIED EXTERNALLY`, `STALE`, `CONFLICT`; anything else is refused as drift, a conflict raises with the plan in the message). It is the one bridge in `client.py` again, argv pinned by a pure test, deleted the day a generated method lands. **Not adopted for the live test suite**: the integration modules `init` a fresh schema each and run unindexed, which is correct by upstream's own contract (the index is speed and lock scope, never the answer); the seed and provision legs exercise the indexed route.

**Step 5, regeneration.** `__init__.py`, `adapter.py`, `envelopes.py`, `session.py`. `MODEL_HASH` unchanged (`sha256:70454686…`), `models.py`, `values.py` and `morpholog_views.sql` byte-identical: no seal churn, no views re-apply. What reached our code:

- **The pack export is generated now.** `audit_export(path, tree_size, timeout)` streams the complete-prefix pack to a file as NDJSON (manifest line, checkpoints, rows) and returns `PrefixPackManifest`; `EvidencePack`/`PackManifest` are gone from the client. - **Also in the client, unused**: `MorphologTimeout` carries the partial stdout/stderr.

**Skew, measured, and the case for morpholog#393.** Neither direction refuses. A v0.0.11 binary proposes and commits against a v0.0.12-migrated schema, and because the equality key is an expression over `arguments`, the v0.0.12 binary's keyed loads still see that row (checked: a v0.0.11 grant, then a v0.0.12 `explain` and `propose` gated on it, both admitted). A v0.0.12 binary against an unmigrated v0.0.11 schema commits a proposal whose loads are not keyed (a grant), and fails one whose loads are with the raw SQL error `function morpholog.value_key_v1(jsonb) does not exist`, reported as the coded `not_committed`. `audit verify` runs on either. So for this release the skew is silent rather than sharp, and a process that missed the migration finds out one transformation at a time. That is the release note's own "nothing checks versions at run time" and the still-open #393; this pass is its Glasshouse evidence.

**Step 6, the twenty-organisation capture, before and after.** The workload is the one morpholog#396 describes, rebuilt (the original script did not survive the session that produced it): twenty organisations at once, each granting three capabilities, registering a curve, capturing ten trades, valuing them and then correcting the curve and re-marking everything in one `transact`, every decision a one-shot `propose` through the Glasshouse flows (payload store, then claim), retried with jittered backoff on a serialization failure up to thirty times. Twenty-two cores, local PG18 (the Timescale image), both binaries from the release channel, both sides through their own generated client. The "10k" ledger is 500 filler organisations with a grant and ten captures each (10,500 claims), `ANALYZE`d before the burst; the two "same ledger" rows restore one v0.0.11 dump for both sides (v0.0.12 then migrates and provisions its 27 indexes over it).

The capture number the issue recorded for v0.0.11 (8.5 attempts at 10k) reproduces at 8.7. **v0.0.12 does not move it**, and its `transact` is worse, so the keyed load has not reached this workload. The reason is measured, not guessed. A sampler read `pg_locks` four times a second through both same-ledger bursts: under v0.0.12 a **relation-level SIRead lock on `morpholog.claims` is held in 88 percent of samples, up to 13 at once** (v0.0.11: 93 percent, up to 15), beside the page locks the keyed loads take. Logging every statement of one organisation's run on that ledger names the statement. Each proposal first runs an arity guard,

```sql
SELECT count(*) AS "malformed!" FROM morpholog.claims
 WHERE (predicate_name = $1 AND jsonb_array_length(arguments) IS DISTINCT FROM 1)
    OR (predicate_name = $2 AND jsonb_array_length(arguments) IS DISTINCT FROM 2) ...
```

one `OR` arm per predicate in scope. For a capture that is `MayCaptureTrade` and `TradeCaptured`: a bitmap heap scan over all 5,010 `TradeCaptured` rows, and inside a SERIALIZABLE transaction it leaves exactly one SIRead lock of type `relation` on `claims` (checked by hand: `EXPLAIN`, then `pg_locks` for the backend, on the probe ledger). The keyed load that follows it (`... WHERE predicate_name = 'TradeCaptured' AND claim_digest(value_key_v1(arguments -> 2)) = ...`) plans as an index scan and leaves one page lock, as the release says. So the guard re-takes, on every proposal, the very lock #400 removed from the load, and any two proposals that write `claims` conflict as before. `transact` runs the guard once per act (eleven times in the correction), which fits its larger regression. The empty-ledger rows are the issue's third point (a tiny table seq-scans) and are not changed by this release either.

**What upstream needs from this**: the guard's scan (the statement above, verbatim, with the `pg_locks` reading), the workload script (kept beside the results, not in this repository), and the number they asked for: retries per commit 4.57 before, 5.10 after, on the same ledger. The demo's own provisioning is unaffected: `provision indexes` is adopted for when the load is keyed all the way down, and the indexes are used (their `idx_scan` counters ran into the tens of thousands during a burst).

**Friction recorded from this pass (not filed; ask first):** `provision indexes` has no generated method and no `--json` (the plan parser above is ours); `init` provisions the schema but not the indexes a fresh database needs, so every embedder must remember a second command (and the nightly reset showed how easy it is to forget); the skew above is silent in both directions (#393's forcing example from this side: a v0.0.12 binary on an unmigrated schema is a raw SQL error on the first keyed load).
